# MemoryBridge Red-Team — 2026-08-06

Five parallel audits (token management, cost efficiency, cross-model bridging, security,
data integrity), with every P0/P1 finding independently re-verified against the live system
before inclusion. Claims that did **not** survive verification are listed at the bottom.

Production data was not modified. Measurements ran against a `VACUUM INTO` copy.
Verified after the audit: 704 memories, 12 pruner_log rows, 0 queued — unchanged.

## P0-1 — The auto-pruner has already permanently destroyed 12 memories, and is still armed

**Verified directly against the live DB.**

`pruner_log` holds 12 hard deletions. Eleven share the **identical timestamp**
`2026-07-23T10:43:27.963884` — one single `add_memory` call — and form an unbroken
supersession chain:

```
mem_9a6729a7 → mem_95ac8ff8 → mem_6a1761d3 → mem_0e3e1b54 → mem_6a92b0b2 → mem_a2e064d3
→ mem_0db67b04 → mem_12b8399e → mem_8e9003ca → mem_885d3cf5 → mem_12067322 → mem_f0a2119e
```

I checked every `superseded_by` target against the live `memories` table:
**11 of 12 superseders are also gone.** Only the chain tail survives. An 11-deep project
history collapsed to a single row in one write.

The 2026-07-08 `verbatim_subset` deletion (`mem_9ef94508`) had superseder `mem_6a419436`
— **also deleted**. That fact now exists nowhere.

**Root cause** — `db/pruner.py:255-305`: `run_auto_prune` builds `all_candidates` once,
then deletes each in a loop **without re-validating** that the superseder justifying the
deletion still exists. `find_stale_project_status` (pruner.py:190-222) only requires that a
newer row exists at enumeration time.

**Still armed.** Live `pruner_rules`:

| rule | confidence | auto_count | queue_count |
|---|---|---|---|
| verbatim_subset | 0.85 | 1 | 0 |
| stale_project_status | **0.85** | 11 | **0** |

`AUTO_EXECUTE_THRESHOLD = 0.85` (pruner.py:33) and the gate is `>=`. `REVIEW_ONLY_RULES`
is `{"verbatim_subset"}` (pruner.py:45) — **`stale_project_status` is not protected** and
sits exactly at the trigger value. It will delete again on the next local `add_memory`.
(`verbatim_subset` appears to have been added to the review-only set *after* its 2026-07-08
deletion — the same retrofit was never applied to the rule that has done 11× the damage.)

**The safety mechanism has never run.** `prune_queue` is empty; `pruner_log` contains zero
`queued`/`user_approved`/`user_rejected` rows. The human-review queue and confidence-learning
loop have never executed in production. Confidence reached 0.85 out-of-band, not through the
designed feedback path.

**Unattended trigger path** — `ingestion/merger.py:14` imports `add_memory` from `server`,
so the launchd inbox watcher runs it with `_REMOTE_MODE = False` →
`allow_auto_delete=not _REMOTE_MODE` = **True** (server.py:412-413). **Dropping a file in
the inbox can hard-delete existing memories with no human in the loop.** The `_REMOTE_MODE`
guard protects only the HTTP bridge; every local write path is wide open.

**Deletion is irreversible and self-erasing.** `db/store.py:611-635` is a hard `DELETE`
with no tombstone. `_log_decision` records IDs only — **never content**. And
`db/store.py:1075-1084` trims `pruner_log` older than 90 days on every `MemoryStore()`
construction, so the 2026-07-23 records vanish ~2026-10-21. Newest backup predates the
loss (2026-07-06); **there is no recovery path for what was already destroyed.**

**Fix order:** (1) add `stale_project_status` to `REVIEW_ONLY_RULES` — one line, stops
ongoing loss; (2) pass `allow_auto_delete=False` for the ingestion process;
(3) re-validate each superseder inside the delete loop; (4) capture content into
`pruner_log` before deleting and exempt it from the 90-day trim.

## P0-2 — The capability token is burned, and there is an unauthenticated remote DoS

**The deployment is live and internet-facing** — `cloudflared` PID 892 serving
`mb.controlaltrecover.com → 127.0.0.1:8484`. (Note: `docs/MULTI_MODEL_FEATURES.md` F3 is
wrong — it describes the tunnel as unbuilt and names `memorybridge.calecorbett.com`, which
is NXDOMAIN. The doc needs correcting.)

### Token exposure (verified by count, value never printed)

| location | evidence |
|---|---|
| `logs/http-bridge.log` | **12 lines** containing the full 48-char token |
| `logs/http-bridge.error.log` | **12 lines** leaking the 4-char prefix (`path=/xxxx/mcp`) |
| `~/Library/LaunchAgents/com.memorybridge.http.plist` | plaintext |
| `…/com.memorybridge.http.plist.bak` | **stale forgotten copy**, plaintext |
| Claude agent session transcripts | ~8 `.jsonl` files |
| **ChatGPT/Perplexity vendor logs** | AWS hosts `44.221.181.252`, `44.210.50.87` fetched `/.well-known/oauth-protected-resource/<TOKEN>/mcp` |

`server.py:1350-1351` claims the token *"never appears in server logs"* and `:1374` says
*"Never print even a prefix."* **Both claims are refuted by the files on disk.** The current
build's mitigation (`access_log=False`) works going forward, but the artifacts were never
purged — and the secret has already egressed to third parties. Treat as compromised.

No rotation mechanism exists anywhere. `server.py:1362` checks `len(token) < 32` only —
a pure length test, no entropy check (`"a"*32` passes). Comparison itself *is* constant-time.

### Unauthenticated 500 + traceback-spam DoS (live-verified)

`server.py:1327-1329` — `secrets.compare_digest` **raises `TypeError` on non-ASCII `str`**
rather than returning `False`, and this runs *before* auth:

```
GET /%C3%A9/mcp        -> HTTP 500   ← crash, pre-auth
GET /wrongtoken/mcp    -> HTTP 404   ← correct
```

I reproduced both against the local bridge. Each 500 writes a ~15-line traceback to
`http-bridge.error.log`, which is **112 MB with no rotation** — `scripts/log_groomer.sh:10`
grooms only `server.error.log`. Anyone who resolves the public hostname can loop this and
fill the boot volume. No token required.

**Fix:** `if not segment.isascii(): return False` before `compare_digest`; wrap `__call__`
in try/except returning a uniform 404; add `http-bridge.error.log` to the groomer.
**Structural fix:** put Cloudflare Access in front of the tunnel — capability-URLs put the
secret in every intermediary's logs by construction, which is exactly what happened.

## P0-3 — Memories are replayed into models with no untrusted-data delimiters

`SECURITY.md` claims memory content is *"wrapped in explicit untrusted-data delimiters."*
That is true only for the **ingestion** direction (`ingestion/extractor.py:44`,
`ingestion/resolver.py:92`). `grep -n "UNTRUSTED" server.py exports.py db/store.py` returns
**zero matches** — the entire **retrieval** path emits raw stored content.

`add_memory` is remote-allowed and applies no injection filtering (only enum validation plus
a length-based guardrail). So a short, innocuous-looking memory written through the bridge
becomes durable, decay-weighted, first-class identity context replayed into **every** future
session across Claude Code, ChatGPT, and Perplexity — ahead of your actual message. This is
a persistent cross-model injection implant with nothing between write and replay.

**Fix:** wrap served content in the same `<<<UNTRUSTED_MEMORY_DATA>>>` fence already used in
`extractor.py` (the pattern exists at `db/reflect.py:23-35` — it just isn't on the export
path), and correct the SECURITY.md claim.

## P1 — Token accounting: budget is real but under-counted (verified: 1.4× at default)

The premise "a relevant slice within a strict token budget" does not hold exactly. Measured
against **your real store** (not synthetic), decoding the actual serialized payload:

| `max_tokens` | reported `served` | actual payload | overrun | memories |
|---|---|---|---|---|
| 1000 | 827 | 952 | 0.95× | 1 |
| 2000 | 1838 | 2420 | 1.21× | 5 |
| **4000 (default)** | 3996 | **5610** | **1.40×** | 13 |
| 8000 | 7999 | 12306 | **1.54×** | 36 |

Overrun **scales with memory count**, confirming a per-memory envelope undercount:

- Per-memory JSON structure is charged a flat `+20` (server.py:189-192, db/constants.py:118)
  but the served row carries `id`, `category`, `importance`, `project_id`, `tags`,
  `token_count`, `created_at` plus `indent=2` whitespace.
- **Tags are served but never charged.** `_RESULT_FIELDS` includes `tags`, but the selection
  loop uses the DB's `token_count`, which is content-only — making `count_memory_tokens`
  (the only function that counts tags) dead code on this path.
- Overhead is measured compact (`json.dumps`) but served indented.

Two related issues:
- **Wrong tokenizer family.** `cl100k_base` (OpenAI) is used throughout while output is
  consumed by Claude, which tokenizes differently. The real overrun is ≥ the table above.
- **No non-circular test exists.** `tests/unit/test_store.py:90-96` asserts
  `sum(m["token_count"]) <= 50` — summing the same field the selector used. A tautology.
  One honest test (`count_tokens(get_memory(max_tokens=N)) <= N`) fails today.

Also: `max_total_tokens: 50000` is **advisory only** — enforced post-insert, and
`effective_score` can't drop below the 0.15 prune threshold until a memory is ~82 days old,
so the ceiling is inoperative for a store's first quarter (exactly when bulk ingest happens).

## P1 — Cross-model bridging: read-mostly broadcast of one profile, not shared memory

1. **`export_for_model` is blocked over the bridge.** It is absent from
   `REMOTE_ALLOWED_TOOLS` (server.py:1222-1232); the boot log confirms it among the removed
   12. The ChatGPT/Gemini/Ollama formatters exist but are reachable **only** from Claude
   stdio and the Streamlit UI — i.e. only you can generate a ChatGPT blob, then paste it
   manually. That is the pre-MCP workflow the bridge was meant to replace. **One-line fix.**

2. **35% of memory is invisible by default.** Remote mode pins `DEFAULT_PROFILE`, and the
   only two tools that *enumerate* profile names are removed — so remote models are
   **discovery-blind, not access-blocked** (passing an explicit `profile` still works).
   Verified live counts:

   | profile | live memories | remote-visible by default |
   |---|---|---|
   | default | 225 (64.7%) | yes |
   | consulting | 56 | **no** |
   | job_search | 41 | **no** |
   | personal | 16 | **no** |
   | teaching | 10 | **no** |

   This worsens over time: `my_router.py` deliberately pulls business content *out* of
   `default`. The better the router works, the blinder remote models get.

3. **Zero write provenance.** The `memories` table has no `source`/`origin_model` column,
   and `log_to_analytics` **hardcodes `model="claude"`** (server.py:348, 627). All 176
   analytics events say `claude`, including calls that demonstrably arrived over the HTTP
   bridge. There is no record anywhere that a non-Claude model has ever touched the system —
   and no way to answer "who claimed this?"

4. **No epistemic status.** A fact you typed and a fact an LLM inferred are byte-identical
   rows. Combined with (3) and append-only remote writes, this is the compounding-slop path:
   model A infers → writes → model B reads as ground truth → infers further.

5. **Remote correction is effectively impossible.** `edit_memory`, `delete_memory`,
   `add_memories` are all blocked. `add_memory(supersedes=[...])` *is* remote-reachable and
   is the intended path, but nothing documents it as such — only 4 of 704 rows have ever
   used it.

6. Read paths hardcode `archived=0` in 14 places with **no `include_archived` parameter and
   no un-archive API** — 356 archived memories are written but unreachable.

## P2 — Cost efficiency

1. **77% of the DB is embedding JSON, most of it dead.** 9 MB of a 12.5 MB DB is vector
   JSON; **440 of 1144 embedding rows are orphans** (parent memory deleted) and 356 more
   belong to archived memories — only 348 memories are live. The FK-cascade cleanup
   (db/store.py:239-254) sits inside a `if not already_init:` branch that never runs on an
   existing DB, so orphans are permanent. Vectors stored as JSON text must be `json.loads`'d
   on every semantic search (~81 ms of parsing per call).
   **Fix:** one-time orphan purge, filter archived in the SELECT, store vectors as `BLOB`.
2. **The prompt-caching commit is a no-op.** `ingestion/resolver.py:109-118` places
   `cache_control` correctly on a stable prefix — but `SYSTEM_PROMPT` is ~200 tokens and the
   minimum cacheable prefix is **1024**. The API silently declines; nothing is ever cached
   or read. Either delete it or verify via `usage.cache_read_input_tokens` (it will be 0).
3. **Sonnet used for a binary accept/reject**, and it rejects 82% (405/496).
   Haiku 4.5 is ~3× cheaper and the existing parser already tolerates its output style.
4. **Extraction uses `deepseek-reasoner`** for schema-constrained JSON extraction — you pay
   a chain-of-thought premium on the task shape that benefits least. Worse, the cheap noise
   regexes run on the model's **output**, so you pay full extraction cost to produce
   "disk usage was 47%" and then discard it. Screen the input instead.
5. **The inbox watcher retriggers itself 200–500×/day, forever.** `ingestion/watcher.py:298`
   opens its lock file with mode `"w"` **inside the directory launchd is watching**, so it
   touches → mtime changes → launchd refires every 10 s. **6415 invocations** logged since
   2026-05-10, nearly all no-ops. One-line fix: move the lock outside the inbox.
6. **112 MB of unrotated logs**, plus ~53 MB of stale unrotated `.bak` DBs.

## Backups are not a safety net

There is **no backup code in the repo** — the `bak-auto-*` files came from outside it.
Of the five backups: one has a **misnamed WAL sidecar** (`.wal` instead of `-wal`), so every
transaction in its 5.6 MB is silently dropped on restore; another was `cp`'d **mid-transaction**
and carries a hot rollback journal. Newest is 2026-07-06 — **before** the 2026-07-23 data loss.

Ten orphaned `.fuse_hidden*` files are byte-identical in header to `memory.db-shm` — SQLite
WAL-index files unlinked while an fd was open, meaning **the data dir was accessed through a
FUSE layer** (Docker/rclone/Cryptomator/sshfs). Clustered on 2026-07-06 10:37–10:54, exactly
coincident with the two broken backups. SQLite over FUSE has unreliable locking — a real
corruption vector. Find and remove whatever mediated that access.

**Fix:** one verified backup via `VACUUM INTO` (single file, WAL-consistent, no sidecar),
with rotation and an actual restore test.

## Claims that did NOT survive verification

Recorded so effort isn't wasted re-checking them:

- **"No index on `memory_embeddings.profile`"** — **false.** `idx_embed_profile` exists.
  The orphan-row and JSON-parse costs are real; the missing-index claim is not.
- **"2.79× token overrun"** — **overstated.** That was synthetic data with 7 tags/memory.
  Measured against the real store: **1.40× at the default budget.** Mechanism confirmed,
  magnitude corrected.
- **"WAL is not checkpointing"** — **false.** `mxFrame=14`, `wal_autocheckpoint=1000`,
  `integrity_check=ok`. The 4 MB file is a high-water mark; SQLite never truncates without an
  explicit TRUNCATE checkpoint. Nothing to fix.
- **"`busy_timeout` unset"** — **false.** Set to 5000 ms at `db/store.py:222`.
- **"The two server instances SIGTERM each other"** — **false.** No `os.kill`/`terminate`
  anywhere. "Superseded by instance PID" is a log string printed *when* a signal arrives, not
  an eviction mechanism. They coexist with `busy_timeout` as the only arbiter — which is what
  makes the cross-process races real rather than theoretical.
- **"The live data dir is in iCloud"** — **false.** `/Users/cale/memorybridge` is on
  `/dev/disk3s1`. The **code** dir is in iCloud (a separate, milder risk).
- **`memory.lock`** — vestigial. 0 bytes, zero code references.
